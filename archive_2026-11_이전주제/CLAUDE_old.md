# CLAUDE.md — 종합설계: 로봇 관절 액추에이터 모델링 및 시뮬레이션 기반 제어 성능 평가

> 이 파일은 Claude Code가 매 세션 시작 시 읽는다.
> 현재 프로젝트는 "구조"만 합의된 상태이고, 내부 모델링(시뮬레이터·태스크·모터·제어기)은 교수님 피드백에 따라 재검토 중이다.
> 3장의 항목은 결정된 것이 아니므로 임의로 확정하거나 구현을 확정 짓지 말고, 조사 결과가 나올 때까지 사용자에게 확인할 것.
> **새 세션(특히 다른 OS나 새 환경)은 먼저 `docs/PROJECT_CONTEXT.md`(지금까지의 목적·이력·규칙·외부 시스템 지도)와 `STATUS.md`를 읽는다.** 설치는 `docs/SETUP_LINUX.md`. 사용자 홈의 기억 파일은 환경을 옮기면 따라오지 않으므로 `docs/claude_memory_backup/`에 복사해 두었다.
> 지도교수 이름이 위 1장(심인욱)과 RCV 프로젝트 제목(유지원)이 서로 다르다. 사용자에게 확인할 것.

## 1. 프로젝트 개요
- 과목: 스마트 모빌리티 공학 종합 설계 (지도교수: 심인욱)
- 목표: 현실적 특성을 반영한 로봇 관절 액추에이터를 모델링하고, 시뮬레이션에서 제어 성능을 평가한다.
- 대상: 1자유도(1-DOF) 회전 관절, 특정 로봇에 종속되지 않는 "Generic Rotary Actuator Joint"

## 2. 합의된 것 (구조 수준)
- 하나의 관절을 대상으로 한다 (1차 회의록 방향). 2자유도 확장은 1자유도 완료 후 여력이 있을 때만
- 액추에이터 체인 구조: Position Command → Controller → Power Electronics → Motor → Gear → Joint
- 역할 분담 방향: 물리 엔진(강체 동역학)은 시뮬레이터가 담당하고, 액추에이터 동역학은 직접 구현한다 (회의록 방향)

## 3. 재검토 중 (교수님 피드백 반영 전, 확정 아님)
| 항목 | 이전 안 | 피드백 / 현재 상태 |
|---|---|---|
| 시뮬레이터 | MuJoCo | "이미 잘 만들어진 시뮬레이터는 없는가" 미답변. 기존 시뮬레이터 비교 조사 후 결정. MuJoCo는 유력 후보일 뿐 확정 아님 |
| 태스크 | Pick-and-Place 데모 | 태스크가 단순하고 검증 난이도가 낮다는 지적. **2026-10-04 사용자 확정(거의 확정): "질량 변화에 대응하는 목표 지점 던지기"로 변경, 연구 후 태스크 발전 가능.** 세부 요구사항·평가지표는 미정 |
| 모터 모델 | DC 모터 2차 전기 모델 | 교수님이 DC 모터는 모델이 지나치게 단순하니 사용하지 말라고 하심. BLDC/PMSM(3상, FOC 포함) 방향 검토 중, 미결정 |
| 제어기 | PID + LQR (이전엔 CTC/SMC 후보도 있었음) | 후보 선정 근거 부족 지적. 문헌 검토 → 비교표 → 시뮬레이션 검증으로 근거를 만든 뒤 결정 |
| 평가지표 / 시험조건 | Settling Time, Overshoot, SSE, RMSE, Control Effort / 스텝, 다중 목표각, 부하 외란, 파라미터 변동 | 태스크·제어기가 바뀌면 함께 바뀔 수 있음. 잠정안으로만 취급 |
| 액추에이터 하드웨어 | 미정 | 요구 사양 산출 후 데이터시트 비교로 선정. 그전 파라미터는 모두 가정값 |
| 적분기 | RK4 | 시뮬레이터 결정에 종속. 잠정 |

구현 시 주의:
- 위 항목이 바뀌어도 크게 다시 짜지 않도록 모터 모델·제어기·태스크를 교체 가능한 모듈로 분리한다
- 모든 파라미터(R, L, Kt, Ke, N, η, 링크 질량/길이 등)는 가정값이며 `config/`에 모은다
- 이 항목들에 대한 결정은 사용자 승인을 받고 `docs/decisions.md`에 이유와 함께 기록한다

## 4. 현재 우선 작업

## 7. 작업 규칙
- 출처가 필요한 주장(논문, 문서)은 `docs/references.md`에 출처와 함께 남긴다. 출처 없이 "일반적으로 그렇다"로 쓰지 않는다
- 선정 근거는 "출처가 명시된 비교표 + 시뮬레이션 결과"로 만든다 (AI가 제시한 후보 목록만으로 근거를 대신하지 않는다)
- 수치 결과에는 사용한 파라미터, 조건, 시드를 함께 저장한다
- 그래프는 matplotlib 정적 PNG로 저장한다
- **지어내지 않는다 (가장 중요한 규칙).** 모르는 값, 받지 못한 파일, 실행하지 않은 결과를 추측으로 채우지 않는다. 파라미터·설정·수치는 출처(파일, PDF, 사용자 발언)가 있는 것만 쓰고, 출처가 없으면 임의로 정하지 말고 사용자에게 묻는다. 할 수 없는 것(MATLAB 실행 불가, 자료 미수령, 두 환경의 정의가 달라 같은 조건으로 맞출 수 없음 등)은 "안 된다"고 먼저 말하고, 비슷해 보이는 값으로 대체해서 PASS를 만들지 않는다. 판정 기준을 바꾸거나 완화할 때는 이유를 밝히고 사용자 승인을 받는다. 실행해서 확인한 것과 문서에서 읽은 것, 추정한 것을 구분해서 쓴다

## 8. 기록 규칙
- 작업을 마칠 때마다 `STATUS.md`를 갱신한다: 한 일 / 결과 요약(수치, 파일 위치) / 결정 사항 / 막힌 점 / 다음에 검토받고 싶은 것
- RCV_NOTE(MCP)에 프로젝트 진행 내용을 기록한다. 기록 형식과 항목은 TBD (사용자 확인 후 추가)
- **RCV(research-note MCP, 교수님이 보는 연구노트)는 쓰기 작업 전에 항상 사용자에게 확인받는다.** log_progress, add_task, update_task, update_stage, advance_stage, update_entry, add_comment, set_review 등 쓰기는 전부 해당한다. 먼저 최종 본문(또는 변경 내용)을 보여주고, 사용자가 그 작업에 대해 "올려" 등 명시적으로 승인한 뒤에만 호출한다. 이전 승인은 다음 작업으로 이어지지 않는다. 읽기(whoami, get_project, list_notices 등)는 확인 없이 해도 된다. RCV 본문에는 확정되지 않은 3장 항목을 확정된 것처럼 쓰지 않고, 가정값·잠정 기준·못 한 것을 반드시 적는다
- RAMS 작업실(팀 artifact)은 교수님이 보지 않으며, 사용자가 맡긴 범위에서는 확인 없이 기록해도 된다. 다만 팀원 칸을 대신 쓰면 그 사실을 칸에 적는다
- 중요한 결정은 `docs/decisions.md`에 한 줄로 남긴다 (날짜, 결정, 이유)
